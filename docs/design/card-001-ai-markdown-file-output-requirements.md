## 0. 一句话概括

本卡片研究一个直觉性假设：

> **当用户要求 AI 不要直接在网页聊天框里回答，而是“把最终输出写成一个可下载的 Markdown 文件”时，AI 的输出长度、结构完整度、内容密度和“努力程度”可能会显著提高。**

这个想法不是先假设它一定正确，而是把它做成一个可长期扩展的静态研究页面：每测试一个 AI 网站，就新增一个实验记录页面；每产生一个新解释，就链接到新的想法页面；每发现一个反例，就回到主页面修正假设。

## 1. 背景与动机

站长观察到，在某些 AI 网页产品中，直接让 AI 在聊天窗口回答时，回答可能相对短；但如果要求它生成一个文件，例如 Markdown 文件，输出可能突然变得非常长，甚至出现数千字、结构完整、像报告一样的内容。

这个现象很值得研究，因为它可能说明：

1. **网页聊天回答**和**文件生成回答**不是同一种产品路径；
2. 同一个模型在不同 UI / 工具 / 工作区中可能表现不同；
3. “让 AI 生成文件”可能会触发一种更偏向“文档生产”的模式；
4. 如果一个 AI 网页能真正生成、编辑、下载文件，它可能不只是简单聊天框，而是具备某种“智能体 / 工具调用 / 工作区执行”的能力；
5. 这种现象可以反过来作为判断 AI 网页能力边界的一种外部测试方法。

本卡片不是为了证明“字越多一定越好”，而是为了探索：

- 为什么有时候**文件化输出**会比**聊天框输出**更长？
- 这种长度增长是否稳定？
- 这种增长是否真的带来质量提升？
- 哪些 AI 网站支持这种能力？
- 这是否能帮助判断一个 AI 网页是不是“更像智能体”？

## 2. 核心假设

### 2.1 主假设 H1

> 对同一个任务、同一个 AI 网站、同一个模型，当用户要求“请把最终输出写成一个可下载的 Markdown 文件”时，AI 的输出长度可能显著高于普通聊天回答。

这里的“显著高于”暂定为：

- 中文字符数 ≥ 普通回答的 1.5 倍；
- 或总字数 / token 估算量 ≥ 普通回答的 1.5 倍；
- 或内容结构明显更完整，例如章节更多、层级更清晰、细节更多。

### 2.2 质量假设 H2

> 文件化输出不只可能更长，也可能更像正式文档：标题、目录、章节、表格、步骤、结论、风险、参考资料等会更完整。

但本假设需要单独评估，不能直接用“字数”替代“质量”。

### 2.3 产品机制假设 H3

> 如果一个 AI 网页可以生成可下载文件、编辑文件、更新已有文件、生成多文件结构，那么它可能在聊天模型之外，还接入了某种工具执行、文档生成、代码执行、工作区或智能体式能力。

注意：这是**外部行为判断**，不是对产品内部架构的确定性判断。我们不能仅凭网页表现就断言其内部实现。

## 3. 本卡片要回答的问题

### 3.1 直接问题

1. 让 AI 输出为 Markdown 文件，是否真的会比普通网页回答更长？
2. 如果更长，是所有 AI 网站都这样，还是只有部分网站这样？
3. 更长的输出是否更好，还是只是废话更多？
4. 要求“Markdown 文件”与要求“Markdown 格式回答”是否有差别？
5. 要求“可下载文件”与要求“代码块里的 Markdown 内容”是否有差别？

### 3.2 间接问题

1. 哪些 AI 网站支持真正的文件生成？
2. 哪些 AI 网站只是把 Markdown 显示在聊天框里？
3. 哪些 AI 网站支持类似 Canvas / Artifact / Workspace 的独立文档区域？
4. 文件生成能力能否作为判断“网页是否具有智能体属性”的信号？
5. 用户如何写提示词，才能稳定触发更长、更完整的输出？

## 4. 关键概念定义

### 4.1 AI 网页

本文中的“AI 网页”指用户通过浏览器访问的 AI 对话产品，例如 ChatGPT、Claude、Gemini、Perplexity、Kimi、豆包、通义千问、DeepSeek 等。

具体测试对象应在实验记录中写明：

- 产品名称；
- 网址；
- 日期；
- 登录状态；
- 付费计划；
- 使用模型；
- 是否开启工具能力；
- 是否支持文件生成；
- 是否支持联网；
- 是否支持 Canvas / Artifact / 文档工作区。

### 4.2 普通聊天回答

指用户直接在聊天框中提问，让 AI 在网页对话流里直接回答，不要求生成文件、不要求下载、不要求创建文档。

### 4.3 Markdown 格式回答

指用户要求 AI 使用 Markdown 语法组织回答，但回答仍然显示在聊天窗口中，用户需要自己复制。

例如：

```text
请用 Markdown 格式回答这个问题。
```

### 4.4 Markdown 文件输出

指用户要求 AI 创建一个 `.md` 文件，最好能直接下载。

例如：

```text
请把最终答案写成一个可下载的 Markdown 文件，文件名为 ai-output-test.md。
```

### 4.5 可下载文件

指网页中出现文件下载链接、附件、导出按钮、生成的文件对象，用户可以下载到本地。

### 4.6 智能体式网页

在本项目中，“智能体式网页”不是严格学术定义，而是一个产品行为概念。

如果一个 AI 网页具备以下能力，就可以认为它更接近“智能体式网页”：

- 可以创建文件；
- 可以编辑已有文件；
- 可以多轮修改同一个文档；
- 可以调用工具；
- 可以执行代码或数据处理；
- 可以生成压缩包、多文件项目、表格、图表等；
- 可以在对话外维护一个工作区；
- 可以根据用户目标拆解任务并产出完整交付物。

这不代表它一定是真正的自主智能体，只代表它的网页交互形式超过了简单聊天框。

## 5. 产品现实背景：为什么这个假设值得测

不同 AI 产品已经在文件、文档、工作区、Artifact、Canvas 等方向上快速演化。当前公开资料显示：

- ChatGPT 的某些 GPT / 工具能力涉及文件生成与下载；如果文件下载失败，OpenAI 帮助文档会建议确认 Code Interpreter & Data Analysis 是否启用。
- Claude 支持 Artifacts，并且 Anthropic 帮助文档说明 Claude 可以创建和编辑文件。
- Gemini 在 2026 年 4 月宣布可在对话中直接生成可下载文件，包括文档、表格、幻灯片等格式。

这些产品变化说明：AI 网页已经不只是“聊天窗口”，而是在向“文档生产环境 / 工作区 / 轻量智能体”发展。因此，本卡片适合作为网站第一个研究型想法。

> 重要说明：AI 产品功能变化很快，所以所有结论都必须记录实验日期。不能把某一天的网页表现当成永久事实。

## 6. 实验设计总览

### 6.1 实验目标

对多个 AI 网站进行同题测试，比较以下几种提示方式带来的输出差异：

1. 普通聊天回答；
2. Markdown 格式回答；
3. 要求生成 Markdown 文件；
4. 要求生成可下载 Markdown 文件；
5. 如果产品支持 Canvas / Artifact / 文档工作区，则要求在该空间中创建完整文档。

### 6.2 实验基本原则

为了避免误判，实验需要尽量控制变量：

- 同一个 AI 网站使用同一个模型；
- 同一个测试任务使用同一份基础问题；
- 尽量在同一天完成同一组测试；
- 不中途追加提示词；
- 不人为鼓励“越长越好”；
- 每个条件至少重复 3 次；
- 保留原始输出；
- 记录是否真的生成文件；
- 单独评价字数和质量。

## 7. 实验分组

### 7.1 A 组：普通回答组

目的：获得基线。

提示词：

```text
请回答以下问题：

【测试问题】

要求：
1. 直接在聊天里回答；
2. 结构清晰；
3. 尽量完整；
4. 不需要生成文件。
```

### 7.2 B 组：Markdown 格式组

目的：测试“Markdown 格式”本身是否导致输出变长。

提示词：

```text
请用 Markdown 格式回答以下问题：

【测试问题】

要求：
1. 使用标题、列表、表格等 Markdown 结构；
2. 直接在聊天窗口里输出；
3. 不需要生成文件；
4. 内容尽量完整。
```

### 7.3 C 组：Markdown 文件组

目的：测试“写入文件”这个要求是否改变输出。

提示词：

```text
请回答以下问题，并把最终答案写成一个 Markdown 文件：

【测试问题】

文件要求：
1. 文件名：ai-output-test.md；
2. 使用完整 Markdown 结构；
3. 包含标题、摘要、正文、分析、结论；
4. 如果你支持生成可下载文件，请直接生成 .md 文件；
5. 如果你不支持生成文件，请明确说明，然后把完整 Markdown 内容放在代码块中。
```

### 7.4 D 组：可下载文件强调组

目的：测试“可下载”是否触发更强的工具路径。

提示词：

```text
请不要只在聊天框里回答。请创建一个可下载的 Markdown 文件，文件名为 ai-output-test.md，并把完整答案写入文件。

【测试问题】

要求：
1. 文件内容必须是完整文章，不是摘要；
2. 文件需要包含清晰标题、目录、章节、分析、例子、结论；
3. 生成完成后，请提供下载入口；
4. 如果当前网页不支持下载文件，请说明原因，并退而求其次输出完整 Markdown 源文。
```

### 7.5 E 组：文档工作区 / Artifact / Canvas 组

目的：测试独立文档空间是否影响输出长度与质量。

提示词：

```text
请在你的文档工作区 / Canvas / Artifact 中创建一份完整 Markdown 文档，用于回答以下问题：

【测试问题】

要求：
1. 不要只给聊天摘要；
2. 文档应当像正式研究报告；
3. 包含摘要、背景、分析、案例、反例、结论、后续问题；
4. 如果支持导出，请尽量支持导出为 Markdown。
```

## 10. 量化指标

### 10.1 长度指标

| 指标 | 说明 |
|---|---|
| 中文字符数 | 去掉空格后统计 |
| 总字符数 | 包含英文、标点、空格 |
| 段落数 | 空行分隔 |
| 标题数 | Markdown `#` 标题数量 |
| 表格数 | Markdown 表格数量 |
| 列表项数量 | `-`、`1.` 等列表项 |
| 代码块数量 | 三反引号代码块 |
| 链接数量 | Markdown 链接或 URL |
| 估算 token 数 | 可以用字符数粗略估算 |

### 10.2 增长倍率

```text
增长倍率 = 文件输出组字符数 / 普通回答组字符数
```

示例：

```text
普通回答：2000 字
Markdown 文件：8000 字
增长倍率：4.0 倍
```

### 10.3 文件生成能力指标

| 指标 | 取值 |
|---|---|
| 是否声称能生成文件 | 是 / 否 |
| 是否实际生成文件 | 是 / 否 |
| 文件是否可下载 | 是 / 否 |
| 文件格式是否正确 | 是 / 否 |
| 文件名是否符合要求 | 是 / 否 |
| 文件内容是否完整 | 1-5 分 |
| 是否支持二次修改文件 | 是 / 否 |
| 是否支持多个文件 | 是 / 否 |
| 是否支持压缩包 | 是 / 否 |

## 11. 质量评分规则

不能只看字数。建议每次输出按 7 个维度评分，每项 1-5 分。

| 维度 | 评分问题 |
|---|---|
| 完整性 | 是否覆盖问题的主要方面？ |
| 结构性 | 是否有清晰层级、章节、总结？ |
| 具体性 | 是否有具体例子、步骤、判断标准？ |
| 准确性 | 是否有明显错误、胡编、偷换概念？ |
| 可执行性 | 是否能拿去直接用？ |
| 克制性 | 是否承认不确定性和边界？ |
| 信息密度 | 是否不是单纯堆字数？ |

总分：

```text
质量总分 = 完整性 + 结构性 + 具体性 + 准确性 + 可执行性 + 克制性 + 信息密度
```

最高 35 分。

### 11.1 重要提醒

站长的原始直觉是：

> 字越多，AI 可能越努力。

这个直觉可以作为研究起点，但不能直接作为结论。更稳妥的说法是：

> 字数增加可能代表模型或产品路径分配了更多输出预算，但它不必然代表质量更高。需要同时检查结构、准确性、信息密度和可执行性。

## 12. “是否是智能体网页”的外部判断框架

本项目不能直接看到 AI 网站内部代码，所以只能做外部行为判断。

### 12.1 一级：普通聊天框

特征：

- 只能在聊天流里回答；
- 不能生成文件；
- 不能编辑文件；
- 不能保存结构化工作成果；
- 用户只能复制文本。

判断：

> 这类网页更像普通聊天界面。

### 12.2 二级：增强聊天框

特征：

- 可以输出 Markdown；
- 可以生成长文本；
- 可以展示表格、代码块；
- 但不能真正创建文件。

判断：

> 这类网页有较强文本能力，但不一定有文件工具能力。

### 12.3 三级：文档 / Artifact / Canvas 工作区

特征：

- 有独立于聊天的文档区域；
- 可以创建和修改文档；
- 可以导出；
- 适合产出长文、代码、页面、报告。

判断：

> 这类网页更像工作区，不只是聊天框。

### 12.4 四级：工具执行 / 文件生成

特征：

- 可以生成可下载文件；
- 可以创建多种文件格式；
- 可以处理上传文件；
- 可以生成表格、代码、压缩包；
- 可能有代码执行、数据分析或文件系统能力。

判断：

> 这类网页具有明显的工具化或智能体化特征。

### 12.5 五级：任务型智能体

特征：

- 能理解目标；
- 能拆解任务；
- 能多步执行；
- 能使用网页、工具、文件；
- 能产出最终交付物；
- 能处理失败并调整路径。

判断：

> 这类网页更接近真正的智能体体验。

## 14. 静态站点实现要求

### 14.1 技术原则

1. 页面跳转只使用 HTML `<a>` 标签；
2. 不使用 JavaScript 实现导航；
3. 首页卡片是静态 HTML；
4. 实验记录页是静态 HTML；
5. 样式使用 Tailwind CSS 编译后的静态 CSS 文件；
6. 不在浏览器运行 Tailwind CDN 脚本；
7. 不依赖数据库；
8. 不依赖服务端；
9. 不依赖前端框架；
10. GitHub Pages 可直接部署。

### 14.2 深色模式要求

站长明确需要深色模式。建议分两级实现：

#### 第一阶段：深色优先 + 系统主题

不使用 JavaScript。网站默认设计成深色风格，或者使用 CSS 的 `prefers-color-scheme` 自动适配系统主题。

优点：

- 完全静态；
- 没有 JS；
- 稳定；
- 适合 GitHub Pages。

缺点：

- 用户不能手动点击切换。

#### 第二阶段：极小 JS 手动切换

如果以后必须支持“按钮切换深色 / 浅色”，可以加入一小段只负责主题切换的 JavaScript。

原则：

- 不让 JS 参与内容加载；
- 不让 JS 参与页面跳转；
- 不让 JS 参与实验数据渲染；
- JS 只负责读取和保存主题偏好；
- 即使 JS 失败，网页仍然能正常阅读和跳转。

## 22. 风险与局限

### 22.1 字数不是质量

长回答可能只是重复、空话、套模板。必须单独评估质量。

### 22.2 产品能力会变

AI 网站功能更新很快。今天支持文件生成，不代表以后一样；今天不支持，也可能明天支持。

### 22.3 模型和账号影响结果

同一网站不同模型、免费/付费账号、是否开启工具、地区、浏览器，都可能影响结果。

### 22.4 提示词本身会诱导长度

如果“生成文件”的提示词天然写得更正式、更长，也可能是提示词差异导致结果变长，而不是文件能力导致。因此 A/B/C 组提示词要尽量公平。

### 22.5 文件生成可能只是 UI 包装

有些产品可能只是把文本包装成文件，不代表模型本身更努力。需要观察文件内容质量，而不是只看是否可下载。

### 22.6 智能体判断不能过度推断

能生成文件不等于一定是智能体；不能生成文件也不等于模型能力弱。这里只能判断网页产品的外部交互能力。
